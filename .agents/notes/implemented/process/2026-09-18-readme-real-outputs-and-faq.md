# Agent Note: README 用真实产出说话，并回答 issue 里反复出现的问题

Status: implemented

## Problem

#171 把 README 排成给人看的顺序，#172 统一了 masthead，但正文仍然全是**说明文字**：读者看到的是「十一个技能把一个点子做成……」「跨镜一致性有三层」这类描述，看不到任何一份 skill 写出来的文件长什么样，也看不到检查器到底会拦什么。同组织的 oh-story-claudecode 在 #434 用真实产出替换说明文字（状态卡、检查链、diff、评分表、lint 输出），效果明显。另一方面，Issues 里反复出现同几个问题——H3 六段提示词要不要全贴（#97）、参考图必须进项目吗（#105）、对白赶读（#106）、口型落错脸（#168）——答案散在 CHANGELOG、方言文件和 issue 回复里，README 没有一处回答。

## Decision

两份 README 在 #171/#172 的骨架上加两个正文段，其余章节保留：

1. **首屏换成 24 秒样片**，`docs/assets/dashboard-zh.png` 下沉到「本地短剧创作台」。样片是套件的最终产物，截图只是辅助工具；这与 #171「截图进首屏」相反，理由是 #126 之后仓库有了真实成片，而 oh-story #434 的经验是视频比截图更能在十秒内说明项目。样片是 9:16 竖屏（768×1344）。用 GitHub 的 markdown 接口实际渲染后发现：`<video>` 上的 `width` 与 `playsinline` 会被 GitHub 剥掉，播放器被包进一个带文件名的 `<details>` 块、固定 `max-height:640px`、靠左，`<p align="center">` 对它不起作用。所以标签写法与 oh-story 完全一致（`width="100%"`），竖屏在 GitHub 上实际显示为 366×640 左对齐，不会占两屏。「由来」三段原文原位保留（「这是什么」之后、「安装」之前）：审稿 agent 建议把它挪到技能表之后让安装更靠前，维护者明确要求留着——这是工作室的真实经历，不是可以压缩的说明文字。
2. **新增「看看它的输出」**，每一段都摘自树内文件或一次真实运行，逐段给出处：
   - `examples/creator-first/EP001` 的 SHOT-EP001-002 穿过剧本、视觉设定（连续性锁）、分镜（视觉依据 + 冻结关键帧）、视频提示词四份文档；
   - `creator_markdown_check.py` 在样例上的 `OK` 输出，以及把样例故意改坏两处（删视觉依据里的周薄森、改 MOTION-003 时长）后的**真实报错**，改坏的副本只在临时目录，不入库；
   - #126 那次实跑的 SHOT-EP001-017「声音」估时行、MOTION-EP001-017 的 H3 六段正文节选（连续性锁面原样出现在 `subject_definitions`，对白只在 `<d>` 内）与 `剪辑单.md` 两段 CUT，以及该次 RUN-LOG 里 `check` / `verify` 抓到作者本人的两条和两条测量结论。这份实跑副本已在 #158 按仓库规则移出当前树，README 明说这一点，并用提交 `004d945` 的永久链接指向完整剪辑单、21 镜分镜与 RUN-LOG；同时写明它们是 v0.6.6 时的产物，用 v0.7.1 检查器重跑会报什么（`edit_tool.py check` 要求逐个写出 13 个未采用镜号；`creator_markdown_check.py` 在 SHOT-018 报 SHT-26），避免读者照抄「至」这种已停止接受的写法；
   - 每段节选开头标出处（手工整理的公开样例 / v0.4.2 实跑 / v0.6.6 实跑即样片那次），节选里的省略一律以「……」标出，表格注明原表行数与节选行数；
   - `evaluations/让你管账号/reference-run` 的 S1 快评 vs S5 全量回填对照表（含两条被推翻的成因）与 `triage.md` 开头的「执行者声明」（操作者事先通读过全书，回填对照偏乐观，示范的是回填机制而不是抽样准确度）、创作简报的来源事实兑现表与 DEV-04 条款；
   - `evaluations/model-behavior-probes.md` 四行观察，保留原表的「可用于什么判断」一栏与样本量。
3. **新增「常见问题」十条**，每条答案压到 issue 实际问的那个事实加一条链接，都能在树内文件里找到出处：H3 六段整体提交（`creator-documents.md`）、`PLAN-*` 挂图（v0.6.5）、点名模型不等于文生视频（`comic-drama-workflow.md` 卡点表）、对白估时与 4.1 字/秒（`minimax-h3.md`、`shot-craft.md`）、说话人绑定（#169）、`orphaned_provider_job` 与 `collect`（`short-drama-produce/SKILL.md`）、无 GPU 与 ffmpeg 要求、Codex/Windows、静态漫剧跳过视频提示词、升级后跑检查器。
4. 安装段把 `npx skills add zenstory-ai/drama-skills -y -g` 放在最前（`docs/open-source-short-drama-pipeline.md` 已用同一条），自然语言安装与手动链接保留；补一行 CHANGELOG 与升级指引。不像 oh-story 那样手写「最新版本 vX.Y.Z」：masthead 的 Release 徽章已经是实时的，CONTRIBUTING 禁止只断言文案的测试，手写版本号没有任何东西能防止它过期。「由来」一字不改；「这是什么」里对应的要点改写成「先预览、确认，再生产」以免同一句话出现两次。
5. 「这是什么」改成四条加粗要点（五份 Markdown、跨镜一致性三层、确认在生产前、成片在套件里），替换原来的两段散文。
6. 新增「贡献」段（Issues 表单入口 + contrib.rocks），masthead 导航第二个锚点从「十一个技能」改为「看看它的输出」。
7. #171 删掉的「不等于」类边界句，这次只在常见问题「点名模型不等于选择文生视频」保留一处——它逐字来自 `docs/comic-drama-workflow.md` 的卡点表，是回答 #105 那类问题最短的一句；「这是什么」里原本写的「渲染成功不等于能看」已删。
8. README_EN 逐段同步，顶部加 `Last synced with README.md: 2026-09-18` 注释；中文文档节选在英文版译成英文并标注 translated，检查器输出保留原文并在下方用英文解释每一行。

9. 维护者看过预览后的三条意见，照改：去掉 masthead 里的「GitHub Issues」按钮行（#172 的社区按钮行在本仓库没有 Telegram/Discussions 可放，只剩一个 Issues 按钮，多余）；删掉样片下面那句指向剪辑单小节的说明；「看看它的输出」对初学者太重，压成三个短小节（一集写出来是什么样 / 写漏了会被指出来 / 样片是怎么剪出来的，约 90 行），原来的六段完整版原样搬到 `docs/real-outputs.md` 与 `docs/real-outputs_EN.md`，README 在小节开头和「延伸阅读」各链一次。

## Alternatives considered

- **把 #126 的剪辑单和 21 镜分镜重新放回树内的 `demo/`，像 oh-story 那样直接链接文件**。最强理由：链接指向当前树，读者不用理解「某次提交」。被否：#158 刚把这份实跑副本移出树外，`evaluations/README.md` 写明「后续完整项目、生成媒体放在仓库外」；为 README 再放回一份会和这条规则打架。永久链接是稳定的，README 里明说了副本不在当前树的原因。
- **只加 FAQ，不加产出节选**。最强理由：FAQ 直接减少重复 issue，产出节选让 README 从 222 行涨到 500 行。被否：用户点名要的是 oh-story #434 的效果，而那次改造的核心正是用真实文件替换说明文字；行数增长集中在代码块，正文散文反而减少了。
- **保留 dashboard 截图在首屏、视频放「演示」段**（维持 #171）。被否见 Decision 第 1 条。
- **把「由来」挪到技能表之后或压成两句**。最强理由：安装命令能提前一屏。被否：维护者要求原样保留，它是这套技能存在的原因，读者也需要知道这不是从零设计的流程。

## Consequences

- 收益：读者不用装就能看到五份文档怎么互相引用、检查器报什么、剪辑单每一刀为什么这么切；issue 里四个高频问题在 README 有了带出处的答案；中英两份内容一致。
- 代价：README 中文 222→380 行、英文 211→434 行（完整版产出节选另占 docs/ 两份约 240 行）；`看看它的输出` 里有三条链接指向历史提交，那次实跑再被改写历史（不会）或仓库改名时要跟着改。
- 未做：没有把改坏样例的副本或检查脚本放进仓库；没有为 README 新增测试（CONTRIBUTING 禁止「只断言文案存在」的测试）。
