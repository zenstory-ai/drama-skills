# Agent Note: 创作台按阶段分视图，服务端解析文档

Status: implemented

推翻 [单页创作台](2026-08-06-single-page-creator-dashboard.md) 里「单页、无 tabs、无视图切换」的决定；该笔记其余约束保留，并在下面 Decision 里重述。[对标提案](../../rejected/feature/2026-09-26-dashboard-benchmark.md)第 4–7 项的内容在这里以分视图的形态落地，第 1–3 项见 [分集进度与首屏](2026-09-26-dashboard-progress-first-screen-copy.md)。

## Problem

- 单页把所有 Markdown 渲染成同一列正文，结构只能靠读文字获得：剧本看不出谁在说话、哪句是旁白；分镜看不出哪里拖、哪里全是中景；设定看不出一个条目在哪几镜出现、锁住了什么。
- 对标提案想在单页里补这些：分镜正文上方加镜头一览、剧本加说话人排版、设定加资产卡、加全文搜索。每一项都要在前端再写一份解析器，与 `creator_markdown_check.py` 靠对照测试维持一致；22 镜的一览加 22 镜的正文，页面长度翻倍。
- 做出的原型经维护者确认：每个阶段一个专门视图、阶段栏兼作本集进度，读得比单页快。

## Decision

**视图与路由**（`skills/short-drama/assets/dashboard/app.js`）

- 全部落在 URL hash 上：`#/` 全剧；`#/EP001` 本集概况；`#/EP001/{script,settings,board,prompts,film,review}[/<ID>]`；`#/files`、`#/file?path=`、`#/edit?path=&at=`。可收藏、可后退。
- 全剧页：下一步（最多三条，必须改的审查意见 → 缺的第一份文档 → 剪辑与渲染）、四个进度数字、分集进度矩阵（手机上是每集一张卡）、已接受的节奏档案、人物、项目文件入口。
- 每集一条阶段栏：概况 · 剧本 · 设定 · 分镜 · 提示词 · 成片 · 审查，每格一个状态点和一个数字。
- 分镜：四个指标对照档案、按时长定宽按景别着色的节奏条、镜头卡或列表、按场次或设定条目筛选；镜头详情抽屉可用 ←/→、j/k 切镜。剧本按剧本排版，对白旁的镜号只来自剪辑单字幕的逐字匹配。成片把剪辑单排成画面、字幕、画面文字、音效四轨，与播放器、剪辑单表联动。
- ⌘K 或 `/` 打开搜索，范围是本集或全剧。
- 某份文档读不出结构时，该视图退回原文渲染，并用一句话说明哪份没读懂；没有归属的文件仍从 `#/files` 可达。

**服务端解析**（`skills/short-drama/scripts/creator_views.py`、`dashboard_server.py`）

- 新增只读接口 `GET /api/series`、`GET /api/episode`、`GET /api/search`，沿用现有令牌、Host/Origin 校验、按描述符或验证路径固定目录、拒绝符号链接与大小上限；两套目录后端都有 HTTP 测试。
- 分镜、视觉设定、提示词直接调用检查器自己的 `_sections`、`_fields`、`_declared_seconds`、`_copyable_prompt`、`REF_RE`/`PLAN_RE`、`_visual_entries`、`_continuity_locks` 等；测试替换检查器的函数，接口结果跟着变。
- 剧本语法归写作技能（`screenplay_index.py`），剪辑单语法归剪辑技能（`edit_tool.py`）。技能各自安装，所以这里各保留一份最小读法，由 `tests/test_dashboard_server.py` 在同一输入上对照原解析器：剧本逐块比对、旁白字数比对 `duration_estimate.measure`，剪辑单逐段比对字幕、画面文字（倒计时、稀有度、接续）与音效。
- `shot_scale` 取「景别/机位」里第一个档位词，`中近景`、`大特写` 整词读出；近景类是近景、特写、大特写、细节，与节奏档案的定义一致。
- 审查只取结论、范围、复核方式和每条意见的位置、证据、影响、修订结果；「规则」行与内部严重度名不出服务端。
- `project_tool status` 新增 `format`：只报格式正确的 `episode_count`、`target_seconds_per_episode`、`aspect_ratio`。`/api/series` 只转出 `title`、`format`、`rhythm_profile`、`lifecycle`。

**媒体只认文档绑定**

- 缩略图只取该镜「输入参考图」里 `用途：起始帧` 的 `REF-…` 路径，且文件存在、未超预览上限。
- 每镜素材只来自剪辑单「来源」行，按剪辑工具的顺序先在本集目录、再在项目根解析；成片取剪辑输出 `制作成果/成片/成片.mp4`。
- 生产技能的输出路径由每个 job 自定，运行记录属于工程内部，没有按 `MOTION-…` 的书面约定，所以没有来源行的镜头显示「待生成」，不按文件名猜。

**编辑与动作**

- 结构视图只读。「编辑原文」打开该文档的 Markdown，从镜头详情进入时光标落在该镜标题；保存走 `PUT /api/file` 带版本号，冲突时不覆盖，提供「复制我的修改」和「载入最新版本」。保存后结构视图按新内容重读。
- 需要写作、修改、生成或渲染的地方只有「复制给助手」，复制一句请求，由创作者贴进对话。逐条复制的标记只存在本机浏览器。

**保留的约束**：浏览器不发起生成或生产提交，投产在对话里确认；Python 标准库服务器加原生 JS，无依赖、无构建；仅回环；Host/Origin 校验；路径包含；拒绝符号链接；原子保存；并发编辑保护；不显示 `.short-drama/`、哈希、协议状态、审查规则编号等工程内部信息。

**视觉**：设计 token 独立成 `tokens.css`（`--zs-*`），与其他 ZenStory 创作台共用同一份文件；`styles.css` 只引用 token，测试断言其中没有裸色值与字体栈。CSP 不允许内联样式，条宽、位置经 `data-css` 由 CSSOM 写入。1440×900 与 390×844 无横向滚动，深浅两套。

## Alternatives considered

- **仍是单页，结构摘要放在正文上方**（对标提案的做法）
  - 最强理由：不推翻已落地决定，没有第二种阅读模式。
  - 不用：每个摘要都是第二条渲染路径加一份前端解析器；摘要与正文同屏，分镜页长度翻倍；原型证明分视图读得更快。
- **前端解析，靠对照测试防漂移**（提案里服务端解析的反面）
  - 最强理由：不新增需要安全评审的 API。
  - 不用：检查器、剪辑工具、前端会有三份解析；接口沿用既有安全边界，新增面只是只读 GET。
- **服务端按路径加载兄弟技能的 `edit_tool.py`**
  - 最强理由：剪辑单只有一份解析器。
  - 不用：技能可以单独安装，CONTRIBUTING 要求改动落在本技能目录；`parse_cut_list` 还只接受文件路径，绕不开固定目录读取。改用最小读法加对照测试。
- **按文件名 `制作成果/videos/SHOT-…` 配每镜素材**
  - 最强理由：生产适配器示例输出正是这样命名，不写剪辑单也能看到素材。
  - 不用：命名不是约定；没绑定的素材挂在镜头旁会被当成已确认的那一条。
- **在浏览器里按字段改时长、景别**
  - 最强理由：改一个数字不用找行。
  - 不用：形成第二条写入路径，与「只保存 Markdown」冲突。

## Consequences

- **收益**：
  - 打开即能答出进度和下一步；每份文档按本来的样子读；审查意见直接链到镜头、场次和剪辑段。
  - 解析与检查器同源，改检查器的规则，创作台跟着变。
  - 搜索覆盖台词、镜头、剧本动作、画面文字、设定、提示词、审查与剪辑。
- **代价**：
  - 前端约 2000 行、样式约 750 行；`creator_views.py` 复制了剧本与剪辑单两种语法，靠对照测试守住。
  - `/api/series` 每次请求解析全部分集，本机项目够用，集数很多时会慢。
  - `tokens.css` 由两个仓库共用，改动要同步。
  - 节奏档案未接受时不做任何对照；审查 Markdown 只是建议结构，写法不同时退回原文。
- **已知上限**：
  - 跨集同名设定条目不聚合，全剧页只列人物。
  - 「下一步」仍不看创作者声明的起点，有意只做提示词的一集会被提示写剧本。
  - 播放头按实际片长与剪辑单总时长等比换算，渲染出的片长有几帧出入时位置略有偏差。
