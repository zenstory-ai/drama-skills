# Agent Note: 每集只保留至多五份创作者文档

Status: implemented

## Problem

v0.5 及以前的默认路径是结构化流水线：每个场次、资产、镜头批次都生成 JSON/JSONL、索引、指纹、覆盖表与 QA 记录。一集要写的结构化 JSON 远多于剧本正文（#39），创作者看不懂也改不动。旧项目里已有被接受的结构化产物，新旧两套真相如何共存必须有明确答案。

## Decision

普通创作路径是 creator-first 五文档：`剧集/<EP>/` 下至多 `剧本.md`、`视觉设定.md`、`分镜.md`、`图片提示词.md`、`视频提示词.md`（`project_tool.py` 的 `CREATOR_DOCUMENTS`），格式约定在 `skills/short-drama/references/creator-documents.md`，跨文档核对由 `creator_markdown_check.py` 机械执行。用户可从任一阶段直接进入，不为流程完整补造名义上游。本集进度由五文档与已有媒体推导，never 设单独的生命周期文件。

`剪辑单.md` 归 `POST_PRODUCTION_DOCUMENTS`：它只回答「已经拿到的素材里哪些帧进成片」，不能改任何一镜的职责、台词或起终状态；缺它不算缺创作文档，导出交接时带上。

legacy v0.5 结构化项目 never 原地迁移：升级时新建项目根，逐集人工转移并重新确认五份文档；旧 JSON/JSONL、生产记录与审计证据只读保留用于追溯；两套创作真相 never 在同一项目根并排维护，也不把五文档反向写回旧目录。回滚即回到旧项目根并继续锁定 `v0.5.0`。

创作台如何展示这五份文档见 [单页创作台](../feature/2026-08-06-single-page-creator-dashboard.md)。

## Alternatives considered

- **继续以结构化产物为默认真相** — 最强理由：字段可机械校验、可标 stale、可绑定审查证据。被否：产出量与创作者阅读脱节，创作者要先理解存储格式才能改一句台词。
- **把旧 JSON/JSONL 自动转换成五文档并视为已确认** — 最强理由：升级零人工。0.6.0 明确否定：转换结果不是创作者确认过的内容，而五文档的意义正是「创作者确认过的真相」。
- **剪辑单作为第六份创作文档** — 最强理由：交接时没有它下一个人得重剪。#123 否定：五文档回答「这一集是什么」，剪辑单回答「素材里选哪些帧」，性质不同，所以只随导出携带。

## Consequences

- **收益**：创作者只读五份中文 Markdown；分镜与视频提示词的引用（`SHOT-`、`IMG-`、`REF-`、`LOCK-`）都能在这五份文件里逐字找到。
- **代价与已知上限**：破坏性升级，两套项目不能并排；结构化路径原有的校验能力要在 `creator_markdown_check.py` 上逐条重建（#93、#102、#122 都是事后补的），每补一条都可能让既有项目拿到 REVISE。三份正文语言可能不同而解析只有一套，锁面与画面代称已两次被咬到（#119、#121）。
